## 〇、共享业务域：「商城履约与账务」

一个自洽的电商世界，四件套共享同一套实体与模块命名（互相可当参照系）：

```
SKU 库存 ──预留(TTL)──► 订单 Order ──幂等支付──► 履约 ──► 发货 spool ──► DLQ
                              │                        │
                              └────────► 账本 Ledger ◄─┘  日终结算 + 对账
```

核心实体（全套题共用这套名字，模型跨题可迁移认知）：

| 实体 | 字段 | 不变量 |
|---|---|---|
| `Inventory` | `on_hand: {sku: qty}`, `reserved: {sku: qty}` | `on_hand >= reserved >= 0`，available = on_hand − reserved |
| `Reservation` | `order_id, sku, qty, expires_at` | 过期必须可被 sweep 释放；一个订单同 sku 只有一条活跃预留 |
| `Order` | `order_id, idem_key, state, lines, total` | 状态机合法流转；同 `idem_key` 重放返回同一单 |
| `Payment` | `idem_key, amount, status` | 同 `idem_key` 重放同结果，绝不双扣 |
| `DeliverySpool` | 待投递队列 + attempts | 重试有退避；超 `max_attempts` 进 DLQ；DLQ 可再驱动 |
| `Ledger` | `accounts`, `entries: []` | **∑debits == ∑credits 任何时刻成立**；entry 只增不删 |
| `Settlement` | 日终批次 | 重跑幂等；settled 后不再入账 |

**设计原则**（继承用户最初定的"已知需求→一串串行事务"）：TASK.md 只给
高层需求（做什么、边界情形枚举），不给模块分解；模型自己决定实现结构。
判定器按事务逐段断言。

## 一、长任务 1：`order_fulfillment`（订单履约与库存）

**定位**：长轴主力题，强模型校准目标 **70-85%**（v2 同族题的历史剖面）。
**条件**：A（纯契约）+ B（契约 + 冻结实施计划）。
**时域**：单进程多线程；判定器用并发探针 + 故障注入 + journal 重放。

### 事务链（需求文档按此组织，模型可见）

| # | 事务 | 需求要点（TASK.md 高层描述） |
|---|---|---|
| T1 | 下单 | 参数校验（qty>0、sku 存在）；`idem_key` 幂等（重放→同单） |
| T2 | 预留 | available 扣减；不足拒绝；**并发不超卖**；TTL |
| T3 | 过期 | sweep 释放过期预留、库存回补、订单取消 |
| T4 | 支付 | 幂等扣款（模拟支付网关）；失败→补偿（撤单+释放，无双释） |
| T5 | 履约 | 状态机合法流转（PENDING→RESERVED→PAID→FULFILLED）；部分履约按行 |
| T6 | 发货 | spool 重试+退避；超限进 DLQ；DLQ 可再驱动 |
| T7 | 恢复 | 进程重启（journal 重放）后：预留/支付/队列不丢不重 |
| T8 | 查询 | 订单状态查询；库存报表（on_hand/reserved/available 自洽） |

### 里程碑（10 × 4-5 断言，0.25 步进）

1. `M1 下单校验`：空行拒绝 / qty≤0 拒绝 / 未知 sku 拒绝 / 默认状态 PENDING
2. `M2 下单幂等`：同 key 重放→同 order_id / 不重复建单 / 重放不重复预留
3. `M3 预留正确性`：available 正确扣减 / 不足拒绝且不部分扣 / 报告自洽
4. `M4 并发超卖`：N 线程抢 1 件库存→恰好 1 单成功 / 无负库存 / 无丢失预留
5. `M5 TTL 过期`：过期后 sweep 释放 / 库存回补精确 / 订单→CANCELLED / 未过期不动
6. `M6 支付幂等`：同 key 重放同结果 / 不双扣 / 失败状态正确
7. `M7 支付补偿`：支付失败→撤单+释放 / 重复释放不发生 / 补偿后库存精确
8. `M8 状态机`：非法流转拒绝（如 PENDING→SHIPPED）/ 合法流转全部放行 / 部分履约按行正确
9. `M9 发货 spool`：重试次数正确 / 退避存在 / 超限→DLQ / DLQ 再驱动成功 / 投递成功出队
10. `M10 恢复与报表`：重启后状态完整（预留/支付/队列）/ 无重复投递 / 报表三数自洽 / journal 可重放

### 判定器要点
- 并发探针：barrier 对齐多线程抢库存/重复释放（确定性复现竞态）
- 故障注入：支付网关脚本化失败（前 k 次失败后成功）；投递脚本化失败
- 恢复探针：跑一半 → kill → 用 journal 重启 → 断言终态
- 全部确定性（种子固定），可 0 token 离线复算

## 二、长任务 2：`payment_ledger`（支付账本与清算）⚠️ 压轴

**定位**：长轴最难题，强模型校准目标 **50-75%**，弱模型 20-40%。
**条件**：A + B（同题 1）。
**为什么难**：硬不变量机检 + 并发 + 幂等重放 + 冲正语义 + 双向对账。

### 事务链

| # | 事务 | 需求要点 |
|---|---|---|
| T1 | 入账 | 复式记账（借贷平衡）；账户/币种校验 |
| T2 | 转账 | 原子；余额不足拒绝；**并发安全**（不丢更新/不双花） |
| T3 | 幂等 | 同 `idem_key` 重放→同结果，绝不双记 |
| T4 | 冲正 | 红冲（只增冲正 entry，不删原 entry）；部分退款；余额正确还原 |
| T5 | 日终结算 | 按账户算净额→结算批次；**重跑幂等**；settled 后拒绝入账 |
| T6 | 对账 | 抓出预埋 3 类错账（缺 entry / 批次不平 / 重复入账）；**干净账本零误报** |

### 里程碑（10 × 4-5 断言）

1. `M1 入账平衡`：每笔 ∑ debit == ∑ credit / 币种一致 / 账户不存在拒绝
2. `M2 账户运算`：余额=该账户净流入 / 多账户独立 / 开户校验
3. `M3 转账原子`：成功双方都动 / 失败双方都不动 / 余额不足拒绝
4. `M4 并发转账`：N 线程互转→守恒 / 无负余额 / 无丢失更新（最终余额=初始±期望）
5. `M5 幂等重放`：同 key 重放同结果 / entry 数不变 / 重放不改变余额
6. `M6 冲正语义`：冲正是新 entry / 原 entry 保留 / 部分退款正确 / 冲后余额=原始-已退
7. `M7 结算批次`：净额计算正确 / 重跑不产生第二批 / settled 后入账拒绝
8. `M8 对账-缺 entry`：注入缺记账→报告指出 / 定位到账户与金额
9. `M9 对账-不平与重复`：注入不平批次→报告 / 注入重复入账→报告
10. `M10 对账-零误报`：干净账本→零报告 / 全部注入都被抓到（双向考官）

### 判定器要点
- **不变量机检**：每个操作后跑 `∑debits==∑credits` 与逐账户余额校验（任何时刻）
- 并发守恒探针：N 线程互转后总余额严格守恒
- 对账注入器：脚本化注入 3 类错账 + 干净账本对照（考双向）

## 三、复用映射：reviewer 新题 + critic fixture

### reviewer 新增第 4 题：`fulfillment_review`（仅 A）
- **素材**：一份**故意有 bug 的履约模块**（order_service.py + inventory.py），
  预埋：超卖竞态、双重释放、DLQ 静默丢失、TTL 未执行 + 一个 bait
  （"看起来手写但可证明最优"的并发辅助模块，禁止修改）
- **判定**（沿用现有 reviewer 五维）：缺陷修复（统计探针）/ 跨模块契约保持 /
  bait 纪律 / 补丁最小性（AST 惩罚）/ 性能探针
- **为什么要它**：长任务考"从零建"，reviewer 考"在别人的代码上精准手术"——
  同一业务域的两种能力，v2 证据显示两者不完全相关

### critic 换 fixture：`ledger_audit`（仅 A，双盲 A/B）
- **素材**：业务代码库双候选（candidate-A/B 各一套 ledger + fulfillment 模块），
  各埋 **4 个业务缺陷**（GT）：① 并发负余额窗口 ② 幂等重放双记
  ③ 重试路径双释放 ④ 对账盲区（漏检一类错账）
- **评分**：GT 命中率（4 项）+ depth（是否有实测验证）+ **0 误报**——
  沿用 v2 方法论与现有金标准流程（多强模型探讨出标准答案后再交给裁判核对）
- **连带收益**：GT 锚定后裁判混判问题显著缓解（当前 4 裁判混判的病根就是
  critic 无 GT 锚点）

## 六、需要用户确认的点

1. 两道长题的事务清单/边界枚举有没有漏（尤其 M 级断言的粒度）

   但每次运行独立、且这正是真实工作中的连续性）
